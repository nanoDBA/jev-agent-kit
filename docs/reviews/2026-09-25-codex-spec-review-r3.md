# Independent follow-up review: Phase 1 client, revision 3

## 1. Verdict

**Revise before implementation, with all five original blockers resolved at the specification level.** Of R01-R18, twelve are resolved and six are partially resolved; the remaining findings comprise five inherited majors, one inherited minor, one new major and one new minor. Revision 3 materially improves the contract, but its claim to resolve every finding is premature, particularly for Score validation, uncalibrated routing, diagnostic metadata, DPA enforcement and mock HMAC behavior.

Reviewed on 2026-09-25 at commit `561493725e2ef7b8e9cb6ada99746e1da98c7667` after fetching origin and rebasing `review/codex-spec` onto `origin/phase-0`. The original review is already present upstream as `9424141`; Git correctly skipped the equivalent old review commit during the rebase. This follow-up changes only this file. No implementation, live API calls, package installs or Beads writes were performed.

This is a review of specified behavior, not evidence that an implementation passes tests. The accepted owner decisions and ADR2 Amendment 1 are authoritative for this review; the residual-risk decision, cooperative deadline and additional test suites are not reopened.

## 5. Offline checks and testability assessment

The following counterexample was executed with standard-library Python and synthetic data, without reading credentials, creating files or opening a socket:

```python
import json
import math

probabilities = {"0": 0.0, "1": 1.0}
weighted_mean = sum(int(k) * p for k, p in probabilities.items())
score = True
confidence = True

assert score == weighted_mean
assert math.isfinite(confidence) and 0 <= confidence <= 1
assert json.loads('{"score":true,"confidence":true}') == {
    "score": True, "confidence": True
}
```

All assertions passed. This demonstrates that the literal checks in story 35 do not themselves reject boolean score/confidence; it does not demonstrate a bug in engine code, which was not implemented or executed. API:287 and 305 defines both fields as numbers, and the public validators must make the distinction explicit.

An offline `hmac.new(None, b"synthetic-identifier", hashlib.sha256)` raised `TypeError`, as expected. More importantly, a keyed HMAC cannot preserve the production transform while requiring neither an explicit key nor a default; R15 is a contract contradiction independent of that particular exception. The other calculations confirmed that 48,000 bytes estimates to 16,000 tokens, 48 KiB estimates to 16,384 tokens, and 100,000 is 40% of 250,000. None measures the vendor tokenizer.

## 6. Questions for the owner and assessment of the resolution claims

The original owner questions about route authority, source-policy residual risk, deadlines and testing exceptions have answers in S:14-28 and ADR2 Amendment 1. No renewed approval is needed for those choices. The remaining policy choices that the spec does not settle are:

1. Must every effective `accept`, including advisory work, require calibrated evidence as story 12 says? The proposed R07 wording follows that definition. If uncalibrated advisory acceptance is desired, explicitly change the route definition and its schema/consumer contract.
2. For shadow gates, should errors remain `ask` under the stated failure-first rule, with adapters ignoring effects in shadow, or should the engine always return `no_advice`? R20 identifies the contradictory promises; neither choice should permit acceptance.
3. What reviewed field/source classification will distinguish non-personal live calls from calls requiring a DPA? Requiring affirmative DPA status for all uncertain cases is a conservative default, not a request to reapprove Amendment 1.
4. Is postal-address handling intended to remain a Phase 1 obligation, be implemented through narrowly supported formats, or be explicitly deferred with a corresponding policy decision? The current omission does not establish an exception to ADR2.

Revision 3 replaces the old "Changes from revision 1" section with "Resolution of review findings". I agree with closing R01-R05, R10-R14, R16 and R17 for the reasons in the disposition table. I disagree with the blanket "resolves every finding" statement at S:7 and the full-closure entries for R06-R09, R15 and R18 at S:306-309, 315 and 318: each has the specific residual issue above.

The core remains domain-neutral and portable in design. Retaining stdlib-only runtime, deferring production parsers and host authority, and treating schemas/tests as implementation deliverables are appropriate. The remaining changes are contract corrections and bounded acceptance cases, not a request to expand Phase 1 into host hooks, calibration research or a new security platform.
