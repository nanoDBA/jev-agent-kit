# Independent review of Phase 1 client specification, revision 2

## 1. Verdict

**Revise before implementation.** Revision 2 has a sound separation of evidence from authority, but its current contracts permit mock approval, reuse of calibration after material egress changes, untransformed data in questions, and credential forwarding on redirects; its unconditional deadline guarantee also lacks a feasible enforcement design. Resolve the five blockers and the ten major findings below before treating the spec as ready for an implementation agent.

Reviewed on 2026-09-25 against commit `d1b321bc8c36ca22f5bbc960742d6459403f7665`, from `origin/phase-0`, in the isolated `review/codex-spec` worktree. This is a specification review, not a claim that implementation defects already exist. No Jev API calls, package installs, Beads writes, or implementation changes were made. Only this review file was added.

### API cross-check and limits of the evidence

The following parts agree with the supplied API documentation: the POST URL, bearer authentication, keyed mixed question sets, top-level served `model`, versioned `jev-1.13.0` and alias refusal as kit policy, Noul's yes probability, Choice's argmax/probability-map shape, Score's weighted result, maximum 255 Choice options, 2-10 Score levels, and the two context limits. Sources: API:11-39, 73-178, 180-322; Models:11-20, 27-40, 58-60. The implementation contract should explicitly include `Content-Type: application/json` from API:16 and avoid sending internal consequence/egress/registry fields as question fields.

API:325-338 documents 401, 422, 429 and 529. Facts:47-62 supports additional SDK error categories, request-ID capture and retry headers; Retries:272 supports `retry-after-ms`. No fixed JSON error-body schema or guarantee that retry headers are present follows from this evidence. Treat all other statuses explicitly, including redirects, 404 and 408; a non-success status must never be validated as a normal answer. Choosing not to retry 408 is a permissible kit policy, not an API correctness defect. The request-ID assertion is supported by Facts:49 rather than a header field shown in the captured API page.

There is no evidence here for a universal questions-per-request cap, exact tokenizer, production Choice confidence formula, or structured Score-legend encoding beyond the documented string legend. Do not turn any of those into an alleged vendor guarantee. Removing Score argmax validation was correct; requiring its weighted mean to agree with its distribution is a different check.

### Offline counterexamples

These checks used only Python standard-library objects and synthetic literals, with no socket opened and no real credential read:

```python
import json
from urllib.request import HTTPRedirectHandler, Request

request = Request(
    "https://api.typesafe.ai/v1/systemone",
    data=b"{}",
    headers={"Authorization": "Bearer SYNTHETIC_NOT_A_KEY"},
)
redirected = HTTPRedirectHandler().redirect_request(
    request, None, 302, "Found", {}, "http://example.invalid/redirect"
)
# Observed on installed Python 3.13.15:
# redirected.full_url == "http://example.invalid/redirect"
# redirected.get_method() == "GET"
# redirected.get_header("Authorization") == "Bearer SYNTHETIC_NOT_A_KEY"

json.loads('{"gate":{"noul":0.9},"gate":{"noul":0.1}}')
# Observed: {'gate': {'noul': 0.1}}

json.dumps({"bound": float("nan")})
# Observed: '{"bound": NaN}'

json.dumps({"text": "-----BEGIN PRIVATE KEY-----\nSYNTHETIC\n-----END PRIVATE KEY-----"})
# Serialized text contains escaped newlines, not the original multiline layout.
```

For R06, consider a three-level risk rubric with indices 0=safe, 1=review, 2=unsafe. The answer below satisfies every check explicitly listed in story 19: exact probability coverage, finite probabilities in range with sum 1, a score in range, and a matching legend. Its score nevertheless contradicts its distribution and can cross a low-risk acceptance threshold:

```json
{
  "type": "score",
  "score": 0.0,
  "legend": {"0": "safe", "1": "review", "2": "unsafe"},
  "probabilities": {"0": 0.0, "1": 0.0, "2": 1.0},
  "confidence": 1.0
}
```

For R02, changing only a customer's declared transform from masking to HMAC, or enabling an additional evidence field under the same policy/profile versions, changes model input without changing the enumerated fingerprint payload. This is a counterexample to story 44's claimed invalidation property even if the question-set version is bumped.

| 62-64 | A scripted transport can test smoke orchestration, cap accounting and artifact formatting. | Actual latency, batching stability and served behavior require explicitly authorized later live measurements. For story 63, the engine's local validator will prevent the deliberately malformed request from reaching the API; define a synthetic, capped, smoke-only transport probe without a production validation bypass. |
| 65 | The public batch helper can test ordering, maximum concurrency and atomic permit use with a recording transport. | Add it to the tested surface and define whether every retry consumes a permit, rate budgets, and queued-work deadline handling. |

No clock seam is necessary to test useful retry behavior. It is insufficient, however, to call the full suite deterministic merely because the transport is synthetic. Likewise, the spec can keep a small public API while allowing narrowly scoped adapter and fault-injection tests; those are testing-policy decisions that should be explicit before implementation.

## 3. Questions for the owner that the spec cannot answer

1. Do you accept the declaration-based residual risk for semantic sensitive classes in free text, and which source populations may use it? ADR2 does not record that acceptance. How should the existing inventory/DPA prerequisites be attested for live use?
2. Is `act` intended to mean "typed evidence accepted" or "the proposed action may proceed"? The engine's label/polarity mapping and the future hook contract depend on that distinction. I recommend reserving authorization to the host and keeping shadow/mock candidate routes separate.
3. Must Phase 1 itself guarantee a wall-clock return across blocked OS operations, or may enforce use remain unavailable until the host adapter supplies a verified outer watchdog? A retry budget alone cannot provide the stated guarantee.
4. May the test policy add a controlled local HTTP adapter suite and narrowly scoped receipt-write faults while retaining the agreed no-clock-seam public behavior tests? If not, which unverified safety claims should be removed from acceptance criteria?
5. Are any production language profiles actually required in Phase 1? If so, which languages and supported syntax? Otherwise the two-profile tests should use fixtures and real parsers should remain Phase 2 work.
6. For Phase 3 action records, what stable action identity must accompany a decision, and which layer owns freshness checks and consume-once enforcement? Learnings:49-55 and 132-134 call for this, but `record_outcome` currently records only a post-action boolean and a note. I would keep execution/host authority in Phase 3 while defining the linking fields now.

These are questions for the next spec revision, not permission requests to implement anything in this review.

## 4. Disagreements with "Changes from revision 1"

- **S:245, threshold shapes and routes:** naming shapes is progress, but the shapes are not yet defined enough to implement identical boundary behavior. Sharing `route=act` between shadow and enforce is unsafe for later consumers. See R07.
- **S:248, fingerprint now includes policy/profile versions:** that fixes only part of the invalidation problem. The question-set egress configuration can still change without a new fingerprint. See R02.
- **S:249, `decide` never raises:** a useful goal for recoverable runtime failures, but the accompanying claim that every configuration failure becomes one record per question needs an error envelope when the questions cannot be identified. It cannot cover process termination or exhausted runtime resources. See R14.
- **S:250-252, receipt failures, mocks and deadlines added:** the additions do not yet compose into a safe contract. The test-only mock approval switch contradicts the invariant, durable recording cannot be promised when receipt writes fail, and socket timeouts do not establish the host deadline guarantee. See R01, R05 and R11-R12.
- **S:253-254, code without a profile and declaration handling:** story 24 still permits a reviewed free-text exception, while the testing text reads as unconditional rejection. The declaration approach honestly recognizes detector limits, but the spec cannot claim the owner already accepted that policy in ADR2. See R09 and R17.

I agree with replacing Score argmax validation, refusing aliases consistently, adding outcome records and explicit CLI contracts, and making source-language support explicit. ADR1 is respected: neither dfinke/Jev nor the official SDK needs to become a dependency. The core's general content-kind design and the Python choice are appropriate; the review calls for precise contracts and scoped tests rather than a domain-specific rewrite.
